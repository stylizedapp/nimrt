# Nim на уровне Rust при более компактном и читаемом коде (Симметричный бенчмарк CoreX + AlgX)

Этот документ содержит результаты **выровненного по алгоритмам и структурам данных** сравнения **Nim 2.2.12 (`corex` + `algx`, `--mm:orc`)** и **Rust 1.96.0 (`lto=fat`, `target-cpu=native`)**.

Все 4 дисциплины приведены к идентичным алгоритмическим условиям и проверены серией из **2 прогревочных (`Warmup = 2`) + 11 замеряемых прогонов (`Runs = 11`)** на простаивающей машине с расчётом `min`, `median`, `mean` и `max`.

---

## 1. Конфигурация стенда и методика

* **Процессор и память:** `AMD Ryzen 3 3200U with Radeon Vega Mobile Gfx` (2 физических ядра / 4 потока SMT, базовая частота 2.6 ГГц, L1D: 32 КБ/ядро, L2: 512 КБ/ядро, L3: 4 МБ), ~6 ГБ ОЗУ (`TotalPhysicalMemory ≈ 5.88 GiB`).
* **ОС и схема питания:** Windows x64, схема питания `Высокая производительность (8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c)`.
* **Компиляция Nim (`2.2.12` + MinGW-W64 GCC `11.1.0`, `--mm:orc` по умолчанию в `nim.cfg`):**
  ```powershell
  nim c -d:danger --opt:speed --mm:orc --threads:on --panics:on --passC:"-march=native -O3 -flto" --passL:"-flto -s" -o:benchmarks/nim_full_suite.exe benchmarks/nim_full_suite.nim
  ```
* **Компиляция Rust (`rustc 1.96.0`, target `x86_64-pc-windows-msvc`, LLVM `22.1.2`):**
  ```powershell
  rustc --edition=2021 -C opt-level=3 -C target-cpu=native -C codegen-units=1 -C lto=fat -C panic=abort -o benchmarks/rust_full_suite.exe benchmarks/rust_full_suite.rs
  ```
* **Скрипт воспроизведения:** [`benchmarks/run_benchmarks.ps1`](../benchmarks/run_benchmarks.ps1) (`nimble bench`).

### Ограничения методики и статистические оговорки

1. **Единственная машина без доверительных интервалов (Single-Machine Caveat):** все замеры получены на одном 2-ядерном ноутбуке (`Warmup = 2`, `Runs = 11` в простое ОС); доверительные интервалы (CI) и прогоны на парке машин не строились. На 2 физических ядрах `mean`/`max` заметно зависят от фоновых процессов ОС и буста частоты.
2. **Разные C/ABI тулчейны (MinGW GCC vs Rust MSVC):** Nim собирается через `x86_64-w64-mingw32` GCC `11.1.0`, а Rust — через `x86_64-pc-windows-msvc` (LLVM `22.1.2`). Это влияет на автовекторизацию, планировщик инструкций и системный аллокатор CRT.
3. **Влияние аллокатора на Дисциплину 3 (`ZeroPack POD` 64 МБ):** в `rust_full_suite.rs` временный `Vec` на 64 МБ создаётся и уничтожается внутри каждой итерации, что в MSVC CRT вызывает `VirtualAlloc`/`VirtualFree` и тысячи soft page faults ядра Windows. В Nim аллокатор процесса удерживает и переиспользует крупные блоки между итерациями. При переиспользовании буфера в Rust эта разница аллокаторов исчезает.
4. **Конфигурация памяти `--mm:orc`:** в ранних черновиках использовался `--mm:arc`, тогда как весь проект (`nim.cfg`) работает на `--mm:orc`. Все итоговые цифры ниже получены строго с **`--mm:orc`** (`benchmarks/run_benchmarks.ps1`). Горячие циклы работают с POD (`seq[int64]`, `ptr UncheckedArray`) и циклических `ref` не создают, поэтому накладные расходы трассировщика циклов ORC в вычислительных ядрах не проявляются.
5. **Хэш-таблицы (`FastMap` 16B SSE2 vs `std::HashMap` vs `hashbrown`):** после обновления `src/algx/swissmap.nim` до 16-байтового SSE2 (`_mm_cmpeq_epi8` + `_mm_movemask_epi8` и 16-байтовый SWAR-фоллбэк под `-d:noSse2`) `FastMap` с `SplitMix64` опережает стандартный `std::HashMap` (c `SplitMix64Hasher`) примерно в **~1.30× по медиане** (`168.02 мс` против `219.03 мс`), но уступает оптимизированному Rust-крейту `hashbrown` (`RustFastMap`) примерно в **~1.25× по медиане** (`134.20 мс` против `168.02 мс`).

## 3. Проверенные инженерные факты (по итогам аудита)

1. **Равенство ёмкости `hashbrown` и `FastMap` ($2^{21}$ слотов):**
   * Проверка `mp.capacity()` у `std::collections::HashMap::with_capacity_and_hasher(1_000_000, ...)` в Rust показала `cap = 1 835 008` ($7/8$ от $2^{21}$), то есть физически `hashbrown` выделяет **ровно $2^{21} = 2\,097\,152$ слота** — столько же, сколько `FastMap` в Nim (`slots = 2 097 152`).
   * При замене дефолтного `SipHash-1-3` в Rust на тот же `SplitMix64Hasher` `std::HashMap` показывает `175.37 мс` (min) / `219.03 мс` (med), а прямой крейт `hashbrown` (`RustFastMap`) — `115.53 мс` (min) / `134.20 мс` (med).
   * Актуальный `FastMap` в `src/algx/swissmap.nim` с 16-байтовым SSE2-пробированием (`_mm_loadu_si128`, `_mm_cmpeq_epi8`, `_mm_movemask_epi8` и 16-байтовым SWAR-фоллбэком под `-d:noSse2`) стабильно обходит `std::HashMap` (**`168.02 мс` против `219.03 мс`**, ~1.30× по медиане), но отстаёт от `hashbrown` (~1.25× по медиане, `134.20 мс` против `168.02 мс`).
2. **Векторная аналитика (Дисциплина 4):**
   * Симметричная 8-аккумуляторная безветвевая развёртка в Rust (`(*p.add(i) > threshold) as usize`) показывает **`40.80 мс` (min) / `43.20 мс` (med)**, что практически на уровне с Nim `algx/simdscan` (**`38.66 мс` (min) / `39.78 мс` (med)**).
3. **Почему в Дисциплине 3 (`ZeroPack POD` 64 МБ) Nim быстрее на цикле прогонов (`13.69 мс` против `54.73 мс` по медиане):**
   * Оба языка генерируют **абсолютно идентичный** буфер из `64 000 004` байт с побайтовым хэшем `0x795e71edd77afe17`.
   * Разница во времени возникает на уровне аллокатора памяти: в Rust `Vec::with_capacity(64 MB)` при выходе из области видимости на каждой итерации вызывает `VirtualFree` (через MSVC CRT heap для крупных блоков), возвращая физические страницы ядру Windows, а на следующей итерации `VirtualAlloc` заново проходит через тысячи soft page faults ядра ОС. Аллокатор Nim (`--mm:orc`) удерживает крупные страницы в пуле процесса и переиспользует их без системных вызовов ядра.

## 4. Главный вывод: зачем нужен Nim и экосистема `corex` + `algx`

Честный симметричный тест на `--mm:orc` доказывает два тезиса:

1. **Нативная производительность без компромиссов на вычислительных ядрах:**
   Когда алгоритмы выровнены (4-поточный 3-Level MSD Radix Sort, 16-байтовый SSE2 SwissTable, 8-канальный суперскалярный скан), **Nim (`-d:danger --mm:orc -march=native -O3 -flto`) выступает на уровне оптимизированного `unsafe` Rust и местами быстрее (`69.06 мс` vs `75.31 мс` min на сортировке, `38.66 мс` vs `40.80 мс` min на скане, ~1.30× быстрее `std::HashMap` по медиане на `FastMap` SSE2 при ~1.25× отставании от `hashbrown`)**.
2. **Читаемость и изоляция низкоуровневого кода:**
   Чтобы получить эти показатели в Rust, в коде потребовались десятки блоков `unsafe`, `std::ptr::copy_nonoverlapping`, `*ptr.add(i)`, `.get_unchecked_mut(...)`, касты в `usize` для `Send`/`Sync` и ручное дублирование циклов.
   В Nim (`corex` + `algx`) низкоуровневые примитивы (`cast`, `ptr UncheckedArray`, release-only `{.push checks: off.}`) инкапсулированы внутри библиотеки `algx`, а шаблоны времени компиляции (`unrollHist4`, `unroll4`, `when isBlittable(T)`) генерируют развёрнутый машинный код при **0 `unsafe`-обёрток на стороне пользователя** и более компактном коде:

   ```nim
   # Внутри algx/ultrasort.nim (шаблон времени компиляции разворачивает 4x цикл):
   unrollHist4(sIdx, eIdx, st.hists[t], int((cast[uint64](dataPtr[it]) shr Shift1) xor SignFlip))

   # На стороне пользователя (чистый безопасный высокоуровневый API):
   let rawBytes = packBin(packets)
   let unpacked = unpackBin[seq[VoxelPacket]](rawBytes)
   ```
