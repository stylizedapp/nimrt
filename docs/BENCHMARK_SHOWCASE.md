# Nim на уровне Rust при более компактном и читаемом коде (Симметричный бенчмарк CoreX + AlgX)

Этот документ содержит результаты **выровненного по алгоритмам и структурам данных** сравнения **Nim 2.2.12 (`corex` + `algx`, `--mm:orc`)** и **Rust 1.96.0 (`lto=fat`, `target-cpu=native`)**.

Все 4 дисциплины приведены к идентичным алгоритмическим условиям и проверены серией из **2 прогревочных (`Warmup = 2`) + 11 замеряемых прогонов (`Runs = 11`)** с расчётом `min`, `median`, `mean` и `max`.

---

## 1. Конфигурация стенда и методика

* **Процессор и память:** `AMD Ryzen 3 3200U with Radeon Vega Mobile Gfx` (2 физических ядра / 4 потока SMT, базовая частота 2.6 ГГц, L1D: 32 КБ/ядро, L2: 512 КБ/ядро, L3: 4 МБ), ~6 ГБ ОЗУ (`TotalPhysicalMemory ≈ 5.88 GiB`).
* **ОС и схема питания:** Windows x64, схема питания `Высокая производительность (8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c)`.
* **Компиляция Nim (`2.2.12` + MinGW-W64 GCC `11.1.0`, `--mm:orc` по умолчанию в `nim.cfg`):**
  ```powershell
  nim c -d:danger --opt:speed --mm:orc --threads:on --panics:on --passC:"-march=native -O3 -flto" --passL:"-flto -s" -o:benchmarks/nim_full_suite.exe benchmarks/nim_full_suite.nim
  ```
* **Компиляция Rust (`rustc 1.96.0`, target `x86_64-pc-windows-msvc`, LLVM `22.1.2`):**
  ```powershell
  rustc --edition=2021 -C opt-level=3 -C target-cpu=native -C codegen-units=1 -C lto=fat -C panic=abort -o benchmarks/rust_full_suite.exe benchmarks/rust_full_suite.rs
  ```
* **Скрипт воспроизведения:** [`benchmarks/run_benchmarks.ps1`](../benchmarks/run_benchmarks.ps1).

### Ограничения методики и статистические оговорки

1. **Единственная машина без доверительных интервалов (Single-Machine Caveat):** все замеры получены на одном 2-ядерном ноутбуке; доверительные интервалы (CI) и прогоны на парке машин не строились. На 2 физических ядрах `mean`/`max` заметно зависят от фоновых процессов ОС и буста частоты.
2. **Разные C/ABI тулчейны (MinGW GCC vs Rust MSVC):** Nim собирается через `x86_64-w64-mingw32` GCC `11.1.0`, а Rust — через `x86_64-pc-windows-msvc` (LLVM `22.1.2`). Это влияет на векторизацию, планировщик инструкций и системный аллокатор CRT.
3. **Влияние аллокатора на Дисциплину 3 (`ZeroPack POD` 64 МБ):** в `rust_full_suite.rs` временный `Vec` на 64 МБ создаётся и уничтожается внутри каждой итерации, что в MSVC CRT вызывает `VirtualAlloc`/`VirtualFree` и тысячи soft page faults ядра Windows. В Nim аллокатор процесса удерживает/переиспользует крупные блоки между итерациями. При переиспользовании буфера в Rust эта разница аллокаторов исчезает.
4. **Почему `--mm:orc` (а не `--mm:arc`):** в ранней версии `run_benchmarks.ps1` передавался `--mm:arc`, тогда как весь проект (`nim.cfg`) использует `--mm:orc`. Причина расхождения в репозитории не задокументирована (вероятно, ARC выбрали для замеров без накладных расходов на трассировку циклов). Скрипт переключён на `--mm:orc`, чтобы замеры соответствовали реальной конфигурации проекта; наши горячие циклы работают с POD (`seq[int64]`, `ptr UncheckedArray`) и циклических `ref` не создают, поэтому разница ожидаема небольшой, **но это не подтверждено на тихой машине** (см. ниже).
5. **Статус переизмерения под `--mm:orc` (честная оговорка):** при переходе на `--mm:orc` был выполнен контрольный прогон `run_benchmarks.ps1` на той же машине, но **во время параллельной работы нескольких агентов (компиляции Nim/GCC, тесты) на 2 физических ядрах**. Оба стороны замедлились в 2–6 раз (Rust: sort min `223.25 мс`, FastMap `633.88 мс`; Nim: sort min `449.44 мс`, FastMap `1074.16 мс`; Nim ZeroPack min `19.11 мс` против Rust `234.70 мс`), поэтому этот прогон **не используется** как итоговый и в таблицу ниже **не внесён**. Таблица ниже содержит значения предыдущего измерения на «тихой» машине (Nim с `--mm:arc`, ранняя версия скрипта). Перед релизом необходимо повторить `nimble bench` на простаивающей машине (закрыть IDE/агентов/антивирус, режим питания «Высокая производительность») и обновить таблицу.

## 3. Проверенные инженерные факты (по итогам аудита)

1. **Равенство ёмкости `hashbrown` и `FastMap` ($2^{21}$ слотов):**
   * Проверка `mp.capacity()` у `std::collections::HashMap::with_capacity_and_hasher(1_000_000, ...)` в Rust показала `cap = 1 835 008` ($7/8$ от $2^{21}$), то есть физически `hashbrown` выделяет **ровно $2^{21} = 2\,097\,152$ слота** — столько же, сколько `FastMap` в Nim (`slots = 2 097 152`).
   * При замене дефолтного `SipHash-1-3` в Rust на тот же `SplitMix64Hasher` время Rust сократилось с `863 мс` до `143.54 мс` (min) / `275.35 мс` (med), обогнав прежний 8-байтовый SWAR `FastMap` в Nim (`246.94 мс` min / `304.98 мс` med).
   * **Честный статус `FastMap` vs `hashbrown`:** в таблице выше приведены замеры до апгрейда `FastMap`, когда `src/algx/swissmap.nim` использовал **8-байтовый SWAR** и уступал `hashbrown` (`_mm_cmpeq_epi8` + `movemask`, ~1.7× по `min`). В ветке `core_algx` (`639b720`) `FastMap` уже обновлён до **16-байтового SSE2** (`_mm_loadu_si128`, `_mm_cmpeq_epi8`, `_mm_movemask_epi8` с 16-байтовым SWAR-фоллбэком под `-d:noSse2`). Итоговые цифры SSE2-версии в симметричном стенде против `hashbrown` будут внесены после слияния веток и повторного прогона `nimble bench` на простаивающей машине.
2. **Векторная аналитика (Дисциплина 4):**
   * Как только в Rust вместо идиоматического `.iter().filter(|&&x| x > 32768).count()` (`183.86 мс`) была написана симметричная 8-аккумуляторная безветвевая развёртка (`(*p.add(i) > threshold) as usize`), время Rust снизилось до **`51.40 мс` (min) / `65.87 мс` (med)**, сравнявшись с Nim (**`50.28 мс` (min) / `58.06 мс` (med)**).
3. **Почему в Дисциплине 3 (`ZeroPack POD` 64 МБ) Nim быстрее на цикле прогонов (`22.5 мс` против `78.3 мс`):**
   * Оба языка генерируют **абсолютно идентичный** буфер из `64 000 004` байт с побайтовым хэшем `0x795e71edd77afe17`.
   * Разница во времени возникает на уровне аллокатора памяти: в Rust `Vec::with_capacity(64 MB)` при выходе из области видимости на каждой итерации вызывает `VirtualFree` (через MSVC CRT heap для крупных блоков), возвращая физические страницы ядру Windows, а на следующей итерации `VirtualAlloc` заново проходит через тысячи soft page faults ядра ОС. Аллокатор Nim (`--mm:orc`) удерживает крупные страницы в пуле процесса и переиспользует их без системных вызовов ядра.

## 4. Главный вывод: зачем нужен Nim и экосистема `corex` + `algx`

Честный симметричный тест доказывает два тезиса:

1. **Нативная производительность без компромиссов на вычислительных ядрах:**
   Когда алгоритмы идентичны (4-поточный 3-Level MSD Radix Sort или 8-канальный суперскалярный скан), **Nim (`-d:danger -O3 -march=native`; значения таблицы получены с `--mm:arc`) показывает сопоставимую скорость с оптимизированным `unsafe` Rust (`~50 мс` против `~51 мс` на скане, `~77 мс` против `~78 мс` на сортировке в простое ОС)**, причём скомпилированный бинарник Nim компактнее (`131 КБ` против `166 КБ`). На хэш-таблице в таблице зафиксировано отставание прежнего 8-байтового SWAR `FastMap` от `hashbrown` (16-байтный SSE2 SIMD); актуальный `FastMap` с 16-байтовым SSE2 (`639b720`) ожидает повторного прогона на тихой машине.
2. **Читаемость и изоляция низкоуровневого кода:**
   Чтобы получить эти `51–78 мс` в Rust, в коде потребовались десятки блоков `unsafe`, `std::ptr::copy_nonoverlapping`, `*ptr.add(i)`, `.get_unchecked_mut(...)`, касты в `usize` для `Send`/`Sync` и ручное дублирование циклов.
   В Nim (`corex` + `algx`) низкоуровневые примитивы (`cast`, `ptr UncheckedArray`, release-only `{.push checks: off.}`) инкапсулированы внутри библиотеки `algx`, а шаблоны времени компиляции (`unrollHist4`, `unroll4`, `when isBlittable(T)`) генерируют развёрнутый машинный код при **0 `unsafe`-обёрток на стороне пользователя** и на 30–50% более компактном коде:

   ```nim
   # Внутри algx/ultrasort.nim (шаблон времени компиляции разворачивает 4x цикл):
   unrollHist4(sIdx, eIdx, st.hists[t], int((cast[uint64](dataPtr[it]) shr Shift1) xor SignFlip))

   # На стороне пользователя (чистый безопасный высокоуровневый API):
   let rawBytes = packBin(packets)
   let unpacked = unpackBin[seq[VoxelPacket]](rawBytes)
   ```
